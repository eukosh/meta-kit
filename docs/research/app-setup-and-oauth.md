# Meta app setup, OAuth flows and what can be automated

Research for [issue #5](https://github.com/eukosh/meta-kit/issues/5). Researched 2026-10-27 against developers.facebook.com only (docs at `/docs/...` and their Markdown mirrors at `/documentation/...`). Graph API version in the docs on that date: v26.0. Where Meta's docs are silent the text says so; the only non-doc evidence is marked "observed" and comes from the Language Ranch Ops app setup.

## Gist

One Meta app can serve Facebook Pages, Instagram (via Facebook Login) and Threads for the user's own assets. Threads gets its own app ID and secret inside that app. The user must do the console work by hand (create app, add use cases, add roles, read the IDs and secrets); the official MCP can only read app settings today and promises app creation and use-case adding "soon". OAuth is the manual flow on `www.facebook.com/dialog/oauth` for Facebook and Instagram, and `threads.com/oauth/authorize` for Threads. Long-lived tokens (60 days) need the app secret for the exchange on every platform, so the tool must hold the user's secrets locally; Meta's "never ship the secret" rule is about third-party distribution, which a bring-your-own-app tool does not do.

## 1. Can one app serve all three platforms?

Meta's app model is now "use cases". Facts from [Create an app](https://developers.facebook.com/docs/development/create-an-app/):

- "You can add multiple use cases to a single app, provided they are compatible with each other." "During initial app creation, after you select a use case, incompatible use cases are greyed out." "If you choose to add additional use cases later, only compatible use cases are displayed."
- Worked example in the same doc: "you can add the Access Threads API use case to an app with the Manage everything on your Page use case, but you can't add the Authenticate and request data from users with Facebook Login use case since it is incompatible."
- "Facebook Login for Business and Webhooks might automatically be added to your app." Use cases cannot be removed once added.
- The "Available use cases" table on that page and on [Use Case Customization](https://developers.facebook.com/documentation/development/app-customization.md) renders empty in the Markdown mirror, so the full compatibility matrix is not in the docs. Meta documents only the one example above.

The three use cases meta-kit needs, as named in the dashboard:

| Platform | Use case (dashboard name) | Source |
|---|---|---|
| Facebook Pages | "Manage everything on your Page". Default permissions `business_management`, `pages_show_list`, `public_profile`; others added per need. | [Pages API use case](https://developers.facebook.com/documentation/development/create-an-app/pages-use-case.md) |
| Instagram | "Manage messaging and content on Instagram". Two setups, "API setup with Instagram login" or "API setup with Facebook login"; "You can only add one setup per app." The Facebook-login setup's "Add all required permissions" adds `business_management`, `instagram_basic`, `instagram_content_publishing`, `pages_read_engagement`, `pages_show_list`. | [Instagram use case](https://developers.facebook.com/documentation/development/create-an-app/instagram-use-case.md) |
| Threads | "Access the Threads API". `threads_basic` required; optional `threads_content_publish`, `threads_delete`, `threads_keyword_search`, `threads_location_tagging`, `threads_manage_insights`, `threads_manage_mentions`, `threads_manage_replies`, `threads_profile_discovery`, `threads_read_replies`. | [Threads use case](https://developers.facebook.com/documentation/development/create-an-app/threads-use-case.md) |

What this means for meta-kit:

- Pages + Threads in one app is documented as allowed. Pages + Instagram (Facebook-login setup) is the standard "Instagram API with Facebook Login" path, which needs the products "Facebook Login for Business", "Instagram > API setup with Facebook login" and (for messaging) Messenger in one Business app ([Instagram Platform overview](https://developers.facebook.com/documentation/instagram-platform/overview.md)). No doc says Instagram and Threads are incompatible; the dashboard is the only source of truth and greys out what it will not combine. The guided setup must handle a greyed-out use case by telling the user to create a second app.
- Consumer-style "Authenticate and request data from users with Facebook Login" must not be chosen; it is the documented incompatible one.
- Threads lives in the same app but with its own credentials: "When creating your app there will be 2 app IDs and app secrets. For Threads API implementation purposes, use the Threads app ID and its corresponding app secret" ([Threads get started](https://developers.facebook.com/documentation/threads/get-started.md)). They are shown at App settings > Basic > "Threads App ID" / "Threads App Secret" ([Threads access tokens](https://developers.facebook.com/documentation/threads/get-started/get-access-tokens-and-permissions.md)).
- The Instagram-login setup likewise has its own "Instagram App ID" under Business login settings ([Business Login for Instagram](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login.md)). Since one app takes only one Instagram setup, supporting "with Instagram Login" later means a second app or dropping the Facebook-login setup; it is not an add-on. Tokens from that setup live on `graph.instagram.com`, with `instagram_business_*` permissions and no Page ([overview](https://developers.facebook.com/documentation/instagram-platform/overview.md)).
- App type cannot be changed: "App types cannot be changed" ([App types](https://developers.facebook.com/documentation/development/create-an-app/app-dashboard/app-types.md)). Instagram requires a Business-type app: "Your app must be a business type app to be able to add the Instagram product" ([Create an Instagram app](https://developers.facebook.com/documentation/instagram-platform/create-an-instagram-app.md)). Facebook Login for Business: "Your Meta app must be a business type app or an app with a use case that supports Facebook Login for Business" ([FLB](https://developers.facebook.com/documentation/facebook-login/facebook-login-for-business.md)). The use-case flow picks the type for you; users with an old Consumer app need a new one.

### Business portfolio

- Not required at creation: the Business step offers "I don't want to connect a business portfolio yet." But "If your app will access data that you don't own or manage, you must connect your app to a business portfolio" ([Create an app](https://developers.facebook.com/docs/development/create-an-app/)).
- Required for system-user (BISU) tokens: "Your app must be associated with a business portfolio, which you have full control" and "Businesses onboarding to your app must have, or be willing to create, a business portfolio" ([FLB](https://developers.facebook.com/documentation/facebook-login/facebook-login-for-business.md)).
- Required for system users at all: a system user is created in a business portfolio and can only get a role in an app owned by the same business ([system users create/retrieve/update](https://developers.facebook.com/docs/marketing-api/businessmanager/systemuser/create-retrieve-update/)).
- Business Verification is only needed for Advanced Access ("Business Verification is required to get Advanced Access", [Access levels](https://developers.facebook.com/documentation/development/graph-api/overview/access-levels.md)) and to publish an Instagram app ("required to connect your app to a business that has completed Business Verification" before publishing, [Create an Instagram app](https://developers.facebook.com/documentation/instagram-platform/create-an-instagram-app.md)). meta-kit users do neither.
- Side effect worth telling users: "Developer and admin roles are limited to 15 apps not connected to a verified business account" ([Create an Instagram app](https://developers.facebook.com/documentation/instagram-platform/create-an-instagram-app.md)). And once an app is connected to a portfolio, "manage roles through Business Manager instead" of the dashboard Roles page ([App roles](https://developers.facebook.com/documentation/development/build-and-test/app-roles.md)).

### Development mode, Standard Access, and who can log in

- "Apps in Development mode can only request permissions from role users" and only permissions "with standard or advanced access levels"; dev-mode data "can only be seen by role users" ([App modes](https://developers.facebook.com/docs/development/build-and-test/app-modes/)).
- Business apps are governed by access levels: "Permissions with Standard Access can only be requested from app users who have a role on the requesting app." All three app types "are automatically approved for Standard Access for all permissions and features available to their app type" ([Access levels](https://developers.facebook.com/documentation/development/graph-api/overview/access-levels.md)). So a bring-your-own-app user gets every Pages/Instagram/Threads permission for themselves without App Review.
- Roles: Administrator, Developer, Tester, Analytics User, plus product testers. Threads: invite via App roles > Roles > Add People > "Threads Tester"; the Threads user accepts under "Website permissions" in Threads account settings ([Threads get started](https://developers.facebook.com/documentation/threads/get-started.md)). Instagram-login setup: add the Instagram account (must be public) under Instagram > API setup with Instagram login or App Roles > Roles ([Create an Instagram app](https://developers.facebook.com/documentation/instagram-platform/create-an-instagram-app.md)). For the Facebook-login path, the person needs a Facebook developer account that can perform tasks (MANAGE, CREATE_CONTENT, MODERATE, ADVERTISE) on the Page linked to the IG account ([IG with FB Login get started](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/get-started/)).
- An app with no logins, API calls or webhooks for 90 days is deemed inactive and "all access tokens associated with the app will be invalidated"; an admin restores it by opening the dashboard, and new tokens must be generated ([Maintaining data access](https://developers.facebook.com/documentation/development/maintaining-data-access.md)). `mtk auth status` should explain this error.

### Redirect URIs and localhost

- Docs: "The full URI must be an exact match, including all parameters, with the exception of the optional state parameter." "Enabling Strict Mode is required for all apps." "Enforce HTTPS ... requires HTTPS for OAuth Redirects" and "All new apps created as of March 2018 have this setting on by default" ([Login security](https://developers.facebook.com/docs/facebook-login/security/)). Threads and Instagram-login dashboards "may have added a trailing slash to your URIs" ([Threads](https://developers.facebook.com/documentation/threads/get-started/get-access-tokens-and-permissions.md), [IG business login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login.md)).
- No Meta doc fetched mentions localhost at all (checked: create-an-app, app modes, login security, manual flow, test login flow, platform settings, basic/advanced settings, Threads and Instagram login pages).
- Observed (Language Ranch Ops, Ads MCP setup): the dashboard refuses to save an `http://localhost` entry under Valid OAuth Redirect URIs, and an unpublished app in development mode accepts the `http://localhost:8765` callback anyway. The dashboard shows a notice to that effect next to the field. The same notice is quoted second-hand in community posts; treat it as dashboard behaviour, not a documented guarantee.
- Whether the same allowance applies to the Threads use-case redirect list (its own "Client OAuth Settings" under the Threads use case settings, [Threads use case](https://developers.facebook.com/documentation/development/create-an-app/threads-use-case.md)) and the Instagram-login "Business login settings" list is undocumented. Threads tokens cannot be obtained with an implicit flow, so the prototype ticket must test a localhost redirect on Threads first.
- Fallback if localhost is refused: the manual-flow doc's desktop route, `redirect_uri=https://www.facebook.com/connect/login_success.html` with `response_type=token`, then read the token from the fragment ([manual flow](https://developers.facebook.com/docs/facebook-login/guides/advanced/manual-flow/)). That needs a webview or a paste step, so it is a last resort.

## 2. Manual console steps (one app, all three platforms)

Every step below is dashboard-only unless section 5 says otherwise.

1. Register as a Meta developer and create an app at `developers.facebook.com/apps/creation/`: App details (name, contact email) > Use cases > Business > Requirements > Overview > Go to dashboard ([Create an app](https://developers.facebook.com/docs/development/create-an-app/)).
2. On Use cases pick "Manage everything on your Page", then add "Manage messaging and content on Instagram" and "Access the Threads API" if still selectable. Do not pick "Authenticate and request data from users with Facebook Login". If one is greyed out, finish this app and repeat for the other use case in a second app.
3. On Business choose "I don't want to connect a business portfolio yet" unless the user wants system-user tokens (then connect the portfolio that owns the assets).
4. Dashboard > Use cases > Customize for each:
   - Pages: click Add on the Page permissions the tool needs (`pages_manage_posts`, `pages_read_engagement`, `pages_manage_engagement`, `pages_messaging`, `read_insights`, ...). Facebook Login for Business settings: Valid OAuth Redirect URIs (see section 1 for localhost), optional configurations ([Pages use case](https://developers.facebook.com/documentation/development/create-an-app/pages-use-case.md)).
   - Instagram: choose "API setup with Facebook login", click "Add all required permissions" and "Add required messaging permissions" ([Instagram use case](https://developers.facebook.com/documentation/development/create-an-app/instagram-use-case.md)).
   - Threads: Add the optional `threads_*` permissions; under its Settings add Client OAuth redirect URIs, Deauthorize callback URL, Data Deletion Requests URL ([Threads use case](https://developers.facebook.com/documentation/development/create-an-app/threads-use-case.md)). Whether the callback URLs are enforced for an unpublished app is undocumented.
5. App roles > Roles > Add People: the user is Administrator already; add "Threads Tester" for the Threads account and accept the invite inside Threads ([Threads get started](https://developers.facebook.com/documentation/threads/get-started.md)).
6. App settings > Basic: copy App ID, App Secret, Threads App ID, Threads App Secret ([Threads access tokens](https://developers.facebook.com/documentation/threads/get-started/get-access-tokens-and-permissions.md)). "It is not possible to programmatically rotate the app secret" ([Basic settings](https://developers.facebook.com/documentation/development/create-an-app/app-dashboard/basic-settings.md)).
7. App settings > Advanced > Security: leave "Native or Desktop App" off (see section 4); "Require App Secret" may stay on since the tool always sends `appsecret_proof` ([Advanced settings](https://developers.facebook.com/documentation/development/create-an-app/app-dashboard/advanced-settings.md)).
8. Leave the app in Development mode / unpublished. Never submit for App Review.
9. Optional, headless route: Business settings > Users > System users > create or pick a system user, assign the Page, Instagram account and app, Generate token with the needed scopes, choose 60-day or non-expiring. Meta shows the token once (observed). API equivalent in section 3.

## 3. OAuth endpoints and token lifecycle

### 3.1 Facebook user token (covers Pages and Instagram with Facebook Login)

- Dialog: `https://www.facebook.com/v26.0/dialog/oauth?client_id={app-id}&redirect_uri={redirect-uri}&state={state}` plus `response_type` (`code` default, `token`, or `code%20token`), `scope` (comma or space separated), `granted_scopes`, `auth_type=rerequest` ([manual flow](https://developers.facebook.com/docs/facebook-login/guides/advanced/manual-flow/)).
- Code exchange: `GET https://graph.facebook.com/v26.0/oauth/access_token?client_id={app-id}&redirect_uri={redirect-uri}&client_secret={app-secret}&code={code}`; `redirect_uri` must equal the one used in the dialog; response `access_token`, `token_type`, `expires_in`. User cancel returns `?error_reason=user_denied&error=access_denied` ([manual flow](https://developers.facebook.com/docs/facebook-login/guides/advanced/manual-flow/)).
- Facebook Login for Business variant: add `config_id=<CONFIG_ID>` to the dialog; configurations are created under Facebook Login for Business > Configurations and set token type (User vs System-user), expiry, assets and permissions. For BISU tokens the dialog must use `response_type=code` and `override_default_response_type=true`, and "Your app can only request logins from web surfaces". Configurations are optional for user tokens: the doc allows adding `scope` to a User access token configuration but recommends against mixing the two ([FLB](https://developers.facebook.com/docs/facebook-login/facebook-login-for-business/)). Plain `scope` without `config_id` is what the Instagram-with-Facebook-Login docs themselves use ([Business login for Instagram, FB login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-facebook-login/business-login-for-instagram.md)).
- That Instagram onboarding dialog (`display=page`, `extras={"setup":{"channel":"IG_API_ONBOARDING"}}`, `response_type=token`) returns in the fragment `access_token` (short-lived), `expires_in`, `data_access_expiration_time` and a ready `long_lived_token` without any secret ([same page](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-facebook-login/business-login-for-instagram.md)). Worth prototyping as a secret-free path; untested here.
- Lifetimes: short-lived "about one to two hours"; long-lived "about 60 days" ([Access tokens](https://developers.facebook.com/docs/facebook-login/guides/access-tokens/)). "Do not depend on these lifetimes remaining the same."
- Long-lived exchange: `GET https://graph.facebook.com/v26.0/oauth/access_token?grant_type=fb_exchange_token&client_id={app-id}&client_secret={app-secret}&fb_exchange_token={short-lived}`. "You can not use an expired token to request a long-lived token." There is no refresh endpoint for server-side flows; the SDK auto-refresh applies to iOS/Android/JS only. Re-login before day 60 ([Get long-lived](https://developers.facebook.com/docs/facebook-login/guides/access-tokens/get-long-lived/)).
- Data access expiry: "The expiration period for data access is 90 days, based on when the user was last active"; re-authorize with `auth_type=reauthorize`. Exempt: `ads_read`, `ads_management`, `business_management`, `pages_manage_ads`, `pages_manage_cta`, `pages_manage_engagement`, `pages_manage_metadata`, `pages_manage_posts`, `pages_messaging`, `pages_read_engagement`, `pages_read_user_content`, `pages_show_list`, `read_insights` and a few more. `instagram_*` permissions are not on the list, so Instagram access via a user token lapses after 90 days idle ([Auth vs data access](https://developers.facebook.com/documentation/facebook-login/auth-vs-data.md)).

### 3.2 Facebook Page token

- `GET https://graph.facebook.com/v26.0/{user-id}/accounts?access_token={long-lived-user-token}` returns each Page with its own `access_token`; the person needs a Page role. Page tokens from a long-lived user token "do not have an expiration date" and expire only when the user token is invalidated (password change, deauthorization, etc.) ([Get long-lived](https://developers.facebook.com/docs/facebook-login/guides/access-tokens/get-long-lived/)). No secret needed for this call.
- Instagram IDs: `GET /{page-id}?fields=instagram_business_account`; the Instagram Graph API uses the user token, the Instagram Messaging API needs the Page token ([IG with FB Login get started](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/get-started/), [business login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-facebook-login/business-login-for-instagram.md)).

### 3.3 System user token (headless escape hatch)

- UI: Business settings > System users > Generate token (overview says the UI is the simplest route, [system users](https://developers.facebook.com/docs/marketing-api/system-users/)).
- API: `POST /{business-id}/system_users` (`name`, `role` ADMIN|EMPLOYEE, admin token) creates one; `POST /{system-user-id}/applications` with `business_app` installs the app; `POST /{system-user-id}/access_tokens` with `business_app`, `scope`, `appsecret_proof`, `set_token_expires_in_60_days=true|false` generates the token; `DELETE /{system-user-id}/access_tokens` invalidates. Caller needs an admin user or admin system user token of the same business ([install and generate](https://developers.facebook.com/docs/marketing-api/businessmanager/systemuser/install-apps-and-generate-tokens/), [create/retrieve/update](https://developers.facebook.com/docs/marketing-api/businessmanager/systemuser/create-retrieve-update/)).
- Lifetime: 60 days if `set_token_expires_in_60_days`, otherwise non-expiring (observed: `debug_token` returns `expires_at: 0`). Standard-access system user tokens "do not expire based on time, though they are still subject to invalidation for other reasons" ([Access tokens](https://developers.facebook.com/docs/facebook-login/guides/access-tokens/)).
- Scope the UI offered in practice (observed, Language Ranch): `pages_*`, `business_management`, `ads_*`; `read_insights` was not offered by the Marketing API use case. Which scopes a system-user token can carry depends on the app's use cases; verify with `debug_token`.

### 3.4 Threads

- Dialog: `https://threads.com/oauth/authorize?client_id={threads-app-id}&redirect_uri=...&scope=threads_basic,...&response_type=code[&state=...]`; `threads_basic` mandatory; code valid 1 hour, single use ([Threads access tokens](https://developers.facebook.com/documentation/threads/get-started/get-access-tokens-and-permissions.md)).
- Exchange: `POST https://graph.threads.com/oauth/access_token` form fields `client_id`, `client_secret`, `code`, `grant_type=authorization_code`, `redirect_uri` (must match) → `access_token`, `token_type`, `user_id`. No implicit flow; the Threads secret is mandatory ([same page](https://developers.facebook.com/documentation/threads/get-started/get-access-tokens-and-permissions.md)). `graph.threads.com` and `graph.threads.net` are both valid hosts ([Threads overview](https://developers.facebook.com/docs/threads/overview/)).
- Short-lived: 1 hour. Long-lived: `GET https://graph.threads.com/access_token?grant_type=th_exchange_token&client_secret=...&access_token=...` → 60 days. Refresh: `GET https://graph.threads.com/refresh_access_token?grant_type=th_refresh_token&access_token=...`, no secret, token must be at least 24 hours old and unexpired; a refreshed token lasts 60 days from the refresh ([Threads long-lived](https://developers.facebook.com/docs/threads/get-started/long-lived-tokens/)). Threads can therefore stay logged in indefinitely if the tool refreshes; Facebook cannot.
- Debug: `GET https://graph.threads.com/v1.0/debug_token?input_token=...&access_token=TH|{app-id}|{secret}` (or a Threads tester's user token); returns `type`, `application`, `expires_at`, `data_access_expires_at`, `is_valid`, `issued_at`, `scopes`, `user_id` ([Threads debug](https://developers.facebook.com/documentation/threads/troubleshooting/debug-access-token.md)). App token form `TH|<APP_ID>|<APP_SECRET>` or `GET /oauth/access_token?grant_type=client_credentials` ([Threads app tokens](https://developers.facebook.com/documentation/threads/get-started/app-access-tokens.md)).

### 3.5 Instagram with Instagram Login (not v1, for the record)

- Dialog `https://www.instagram.com/oauth/authorize` (`client_id` = Instagram App ID, `response_type=code`, `scope` of `instagram_business_*`, optional `enable_fb_login`, `force_reauth`, `state`); exchange `POST https://api.instagram.com/oauth/access_token` with `client_secret`; code valid 1 hour; strip a trailing `#_` from the redirect ([Business login for Instagram](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login.md)).
- Short-lived 1 hour; long-lived `GET https://graph.instagram.com/access_token?grant_type=ig_exchange_token&client_secret=...&access_token=...` (60 days); refresh `GET https://graph.instagram.com/refresh_access_token?grant_type=ig_refresh_token&access_token=...` with the same 24-hour / unexpired rule and no secret ([access_token reference](https://developers.facebook.com/documentation/instagram-platform/reference/access_token.md), [business login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login.md)). Same shape as Threads.
- The dashboard also offers "Generate token" per added Instagram account under Instagram > API setup with Instagram business login ([get started](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/get-started/)), a paste-a-token route like the system user one.

### 3.6 Inspecting Facebook tokens

- `GET https://graph.facebook.com/v26.0/debug_token?input_token={token}&access_token={app-token or app developer's user token}`. Fields: `app_id`, `application`, `expires_at`, `data_access_expires_at`, `is_valid`, `issued_at`, `scopes`, `granular_scopes` (`scope` + `target_ids`), `user_id`, `profile_id`, `error`, `metadata`. The reference lists no `type` field even though the Access Token Debugger UI shows one ([debug_token](https://developers.facebook.com/docs/graph-api/reference/debug_token/?locale=en_US)). `granular_scopes` is how the tool can tell which Pages or IG accounts a scope covers.
- App token: `GET https://graph.facebook.com/oauth/access_token?client_id=...&client_secret=...&grant_type=client_credentials`, or just `access_token={app-id}|{app-secret}` ([Access tokens](https://developers.facebook.com/docs/facebook-login/guides/access-tokens/)).

### 3.7 Login for Devices (alternative worth noting)

`POST https://graph.facebook.com/v26.0/device/login` with `access_token={app-id}|{client-token}` and `scope`, user visits `facebook.com/device` and types a code, client polls `/device/login_status`; needs "Login from Devices" enabled under Facebook Login > Settings; token "may be valid for up to 60 days"; no app secret anywhere ([Login for Devices](https://developers.facebook.com/docs/facebook-login/for-devices/)). The doc says scopes "must be approved in Login Review" and does not say whether it works with Facebook Login for Business apps or Page permissions; untested. It would remove the secret and the localhost redirect from the Facebook path, so it is a candidate for the prototype ticket.

## 4. App secret handling for a public desktop tool

- Meta's rules: "Never include your App Secret in client-side or decompilable code"; "the App Secret or an App Access token should never be included in any code"; "Never share your app secret with anyone" ([Login security](https://developers.facebook.com/docs/facebook-login/security/), [Access tokens](https://developers.facebook.com/docs/facebook-login/guides/access-tokens/)). The threat model is a developer distributing their own secret to strangers. meta-kit ships no secret; each user's secret stays on that user's machine, used only against that user's own app. That is the same position as youtube-kit with a Google client secret.
- Where the secret is unavoidable: Facebook long-lived exchange (`fb_exchange_token`), Threads code exchange and long-lived exchange, Instagram-login code exchange and long-lived exchange, system user token generation (`appsecret_proof`), app tokens for `debug_token`. Secret-free: Facebook short-lived token via `response_type=token`, the Instagram onboarding dialog's `long_lived_token`, Page tokens from `/me/accounts`, Threads and Instagram refresh, Login for Devices.
- `appsecret_proof`: `hash_hmac('sha256', access_token, app_secret)` hex, sent as a query parameter on every Graph call; a time-stamped proof is "considered expired after 5 minutes"; the dashboard's "Require App Secret" toggle enforces it ([Securing requests](https://developers.facebook.com/docs/graph-api/securing-requests/), [Login security](https://developers.facebook.com/docs/facebook-login/security/)). The tool should always send it; it is free and lets users keep the enforcing setting on.
- "Native or Desktop App" toggle: when on, "we assume that your native app contains the App Secret or an App Access Token in the binary, and we do not allow calls signed with an App Access Token to proceed" ([Login security](https://developers.facebook.com/docs/facebook-login/security/)). That would break `debug_token` with an app token and system-user token generation. The guided setup should tell users to leave it off; the tool is effectively the user's own backend.
- Secret storage: Meta has no guidance beyond "reset it immediately" if compromised, from App settings > Basic ([Basic settings](https://developers.facebook.com/documentation/development/create-an-app/app-dashboard/basic-settings.md)). The storage ticket decides (OS keychain vs 0600 file); the research only fixes that both the Meta secret and the Threads secret must be stored, and that `mtk auth status` must never print either or any token.

## 5. What can be automated

"API" means Graph API with the user's own credentials; "MCP" means the official Meta Social Technologies MCP at `https://mcp.facebook.com/devtools` (beta, OAuth sign-in with the developer account, 11 tools, "Webhooks are the only area the server can write to", 6 app-lifecycle tools "coming soon": `devtools_app_create`, `devtools_app_use_cases`, `devtools_app_use_cases_manage`, `devtools_business_list`, `devtools_business_create`, `devtools_app_business_manage`; 15 creates per day; "The app secret is never returned") ([devtools MCP](https://developers.facebook.com/documentation/mcp/devtools-mcp)). The Ads MCP and WhatsApp MCP do not touch app config ([MCP overview](https://developers.facebook.com/documentation/mcp)).

| Setup step | Today | Later | Notes |
|---|---|---|---|
| Developer registration | Link only | – | No API. |
| Create the app | Link only | MCP `devtools_app_create` (announced, "no use cases or Business Portfolio") | Graph `POST /{business-id}/owned_apps` is documented as creating an Application but with no parameters and no stated token; unusable as documented ([owned_apps](https://developers.facebook.com/docs/marketing-api/reference/business/owned_apps/)). |
| Add use cases | Link only | MCP `devtools_app_use_cases_manage.add_use_case` (announced; cannot remove) | Compatibility matrix is not in the docs; `list_available` would expose it per app. |
| Pick permissions inside a use case | Link only | – | No API or MCP tool documented. |
| Connect a business portfolio | Link only | MCP `devtools_app_business_manage.link_app_to_business` (announced) | |
| Add app roles / Threads tester | Link only | – | `GET /{app-id}/roles` reads roles with an app token; POST/DELETE are "cannot be performed on this endpoint" ([roles](https://developers.facebook.com/docs/graph-api/reference/application/roles/)). The tool can verify the user holds a role. |
| Read App ID, secret, Threads App ID and secret | Paste by hand | – | MCP `devtools_app` reads `basic_settings`/`security` but the secret is never returned; `GET /{app-id}` with an app token reads settings but needs the secret first. |
| Valid OAuth Redirect URIs | Link only, or rely on the dev-mode localhost allowance | – | The Application node's update parameters have no redirect-URI field ([Application](https://developers.facebook.com/docs/graph-api/reference/application/?locale=en_US)); MCP has none. |
| App domains, website URL, privacy URL, deauth callback | API `POST /{app-id}` with app token (`app_domains`, `website_url`, `privacy_policy_url`, `deauth_callback_url`, ...) if "Allow API access to app settings" is on ([Application](https://developers.facebook.com/docs/graph-api/reference/application/?locale=en_US), [Advanced settings](https://developers.facebook.com/documentation/development/create-an-app/app-dashboard/advanced-settings.md)) | – | Not needed for an unpublished app. |
| Facebook Login for Business configurations | Link only | – | No API documented. Not needed: plain `scope` works for user tokens. |
| OAuth login (all three) | Tool runs it | – | Section 3. |
| Long-lived exchange, refresh, Page tokens | Tool runs it | – | Section 3. |
| Verify token scopes and assets | API `debug_token` (`granular_scopes`), `/me/accounts`, `/{page}?fields=instagram_business_account`, Threads `/debug_token` | – | This is how `mtk auth guide` can say what is still missing. |
| Verify app health, rate limits, compliance | MCP `devtools_app`, `devtools_api_usage`, `devtools_compliance` (read) | – | Optional; requires the user to add the MCP and sign in separately. |
| System user and token | API (section 3.3) given an admin token of the business | – | Chicken-and-egg: needs a prior admin token, so in practice the UI "Generate token" plus paste. |
| Webhooks | MCP `devtools_webhook_manage` | – | Out of scope for meta-kit. |

Net: the guided setup opens pages and verifies results; it cannot press buttons for the user until the announced MCP lifecycle tools ship, and even then permissions, roles and redirect URIs stay manual. The Instagram and Threads "Generate token" / system user "Generate token" buttons are the fastest zero-OAuth path for one person's own assets and belong in `mtk auth login --token` as the paste route.
